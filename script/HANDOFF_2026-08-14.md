## The real problem found today: convergence rate

Only **22–26%** of v2's 825 trials/scenario actually satisfy the strict convergence
check (`sensor_shift < 1e-3`) within 50 AD-iterations. Wildly map-dependent (map 4134:
73–81%; map 17: 5%). Most trials are ending at an arbitrary iteration-50 cutoff, not a
real equilibrium — this is almost certainly why every measurement this whole revision
effort has produced has been unstable/reversing.

**Root cause, found by diff against `attacker_defender_game_iterative_Monte_Carlo.ipynb`**
(a separate, more recently touched notebook in this same dir — Cell 5, edited
2026-08-11) — that notebook has 5 validated fixes that `restored_final_v2.py` (and
the whole `restored_final.py` lineage) never got:

1. **Attacker NLP warm-start** — v2 cold-restarts the attacker's NLP from the raw RRT
   path every AD-iteration; the fixed notebook warm-starts from the previous
   iteration's dense solution. Their own comment: cold-restart made the solver
   "extremely sensitive to tiny defender-position changes... jumping ~35 units to an
   unrelated local optimum."
2. **Attacker-side damping** — v2 only damps the defender (`rho=0.3` on S); attacker
   A is undamped. Fixed notebook damps both.
3. **Windowed convergence check** — fixed notebook adds: last 4 iterations all under
   relaxed tolerance (`sensor_shift<0.1`, `cost_diff<1e-3`) counts as converged, in
   addition to the strict single-iteration check. v2 only has the strict check (and
   doesn't even use `cost_diff` in it).
4. **`vehicle['radius']` bug**: fixed notebook uses 2 (matches the attacker NLP's real
   safety_margin = vehicle_radius(1)+buffer(1) = 2); v2 uses 1, so STP-RRT* hands the
   NLP an initial guess that already violates its own obstacle constraint.
5. **`N_attk` 250 → 100**: fixed notebook uses 100 (still 339x oversamples the fastest
   camera sweep period; numerically more robust). v2 uses 250.

## UPDATE (later same evening): likely found why the fixes aren't landing

Smoke test progressed to 12 trials on map 17: **1/12 converged**, 10 hit
`max_iter_reached`, and **39 separate `Infeasible_Problem_Detected` IPOPT failures**
logged along the way (vs a much lower rate pre-fix). That's the new, useful signal.

**Hypothesis**: the attacker-side damping fix (#2 above) is the culprit, and it's a
different situation from the defender's damping that inspired it. Defender damping is
safe because `S = p0 + alpha*v` is *affine* in alpha, so a convex combination of two
feasible S's is still on the same building edge (still feasible) by construction. The
attacker's trajectory `A` has **nonlinear** feasibility constraints (log-sum-exp
obstacle avoidance, distance safety margins) — a straight-line convex combination of
two obstacle-avoiding trajectories (`A_star = rho*A_raw + (1-rho)*A_prev`) can easily
cut through an obstacle that both endpoints route around. That would produce a
blended `A_star` that's already infeasible, which then gets fed back in as next
iteration's warm-start (`A_init`), likely compounding rather than damping the
instability — consistent with the burst of `Infeasible_Problem_Detected` errors and
the still-low convergence rate.

**If this diagnosis is right, the fix is probably**: damp only the defender (revert
attacker-side damping to v2's undamped behavior) while *keeping* the attacker
warm-start (#1) — since warm-start alone should still smooth iteration-to-iteration
jumps without introducing infeasible blended trajectories. Try that combination on
the same two maps (17, 55) before re-testing the full fix set. Not yet tried as of
this handoff — smoke test (PID 6363) is still running the original 5-fix v3 on map
17/map 55; check `smoke_v3.log` (or the `smoke_v3_snapshot.log` copy here, which is
stale as of this update) for how it finishes.
